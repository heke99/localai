# DIV3RSA Supabase Auth email templates

Production sender for all Supabase Auth emails:

- Sender name: `DIV3RSA`
- Sender email: `system@div3rsa.com`
- Site URL: `https://system.div3rsa.com`
- SMTP provider: Resend

The application owns the token exchange endpoint at `/auth/confirm`. Auth emails use `TokenHash` and send users through that endpoint so the server verifies the one-time token and establishes the Supabase session before redirecting.

## Cross-device requirement

All email verification links are device-independent by design:

- a link requested on desktop may be opened on mobile, tablet or another computer
- no originating browser cookie, localStorage value, PKCE verifier or previous session is required
- the signed one-time `TokenHash` in the email is the verification credential
- a successful verification creates the authenticated session on the device that opened the link
- links always use the canonical HTTPS production origin `https://system.div3rsa.com`
- verification responses are `no-store` so token-bearing URLs are not cached by the application
- every mail includes both a clickable action and a visible fallback URL so restrictive mobile mail clients do not make the flow unusable

## Reset password / first password

This one template supports both onboarding and normal password recovery. The application supplies a same-origin `redirectTo` ending in either `?mode=onboarding` or `?mode=recovery`. Keep `{{ .RedirectTo }}` in the template instead of hard-coding one mode.

Subject:

`Skapa eller återställ ditt lösenord`

HTML:

```html
<h2>Välj ett nytt lösenord</h2>
<p>Följ länken nedan för att välja ett nytt lösenord för ditt DIV3RSA-konto.</p>
<p>
  <a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery&next={{ .RedirectTo }}">
    Välj nytt lösenord
  </a>
</p>
<p>Om knappen inte fungerar kan du öppna den här länken:</p>
<p>{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery&next={{ .RedirectTo }}</p>
<p>Om du inte begärde detta kan du ignorera mailet.</p>
```

Expected application redirect targets:

- First password after approved invite: `https://system.div3rsa.com/auth/set-password?mode=onboarding`
- Forgot password: `https://system.div3rsa.com/auth/set-password?mode=recovery`

## Reauthentication / privileged email verification

Privileged sessions do not use an authenticator app. After a successful password sign-in the application calls Supabase Auth `reauthenticate()`. Supabase generates the one-time code and sends it through the same production SMTP configuration and sender.

Subject:

`Din verifieringskod för DIV3RSA`

HTML:

```html
<h2>Verifiera din inloggning</h2>
<p>Använd den sexsiffriga engångskoden nedan för att fortsätta till DIV3RSA.</p>
<p style="font-size:28px;font-weight:700;letter-spacing:6px">{{ .Token }}</p>
<p>Koden gäller under en kort tid. Om du inte försökte logga in kan du ignorera mailet.</p>
```

Application security for this code:

- exactly six digits
- generated by Supabase Auth using its cryptographically secure OTP generator
- hash validation matches Supabase Auth's canonical SHA-224(email + code) reauthentication path
- accepted for at most 5 minutes by the application
- a challenge is explicitly bound to the Supabase `session_id` that requested the code
- failed guesses are counted per superadmin account across all devices and browser sessions
- at most 5 failed attempts in the rolling protection window before a 15-minute account-wide lock
- signing out, opening another browser or creating another session does not reset the brute-force counter
- the code is consumed after successful verification
- privileged step-up expires after 12 hours or when the underlying auth session ends
- sent, failed and successful verification events are audited without storing the plaintext code

The six-digit privileged step-up code intentionally remains session-bound. The email itself can be opened anywhere: for example, a code requested on desktop can be read from the user's mobile inbox and entered on desktop. If the superadmin wants to complete the verification inside the mobile browser instead, they sign in on mobile and request a code for that mobile session. Email verification and password-reset links, in contrast, are explicitly cross-device and may be opened on another device without signing in there first.

- `https://system.div3rsa.com/auth/accepted`
- `https://system.div3rsa.com/auth/set-password`

## Security requirements

- Resend click tracking: OFF
- Resend open tracking: OFF
- Email confirmation: ON
- Leaked password protection: ON before external production access
- Keep Supabase Auth email rate limits enabled
- Never expose `SUPABASE_SECRET_KEY` to the browser
